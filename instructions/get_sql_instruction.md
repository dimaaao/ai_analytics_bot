### ГЛАВНОЕ ПРАВИЛО ТАБЛИЦЫ (Логика поля `dt`)
Таблица сгруппирована по дате (`dt`) и UTM-меткам. 
Поле `dt` является **универсальным календарем**. В зависимости от выбранной метрики, дата `dt` означает разные события:
- Для базовых расходов и регистраций `dt` = дата совершения события.
- Для метрик с суффиксом `_by_dt_of_payment` `dt` = дата платежа.
- Для метрик с суффиксом `_by_dt_create` `dt` = дата создания лида.
- Для метрик с суффиксом `_by_dt_potok` `dt` = дата старта потока.

Всегда фильтруй или группируй данные по полю `dt`, но правильно выбирай саму метрику (с нужным суффиксом) в зависимости от того, какую когорту просит пользователь.

### СТРУКТУРА ДАННЫХ

**1. Измерения (Dimensions)**
* `dt`: Универсальная дата когорты/события.
* `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`: Стандартные UTM-метки.
* `targetolog`: Имя таргетолога (подтягивается из справочника).
* `channel`: Рекламный канал.
* `channel_aggregated`: Источник (база, органика либо холодный трафик).
* `webname`: Название вебинара.

**2. Рекламные расходы и трафик (Costs & Traffic)**
* Базовые (по дате клика/расхода): `spend_USD`, `spend_KZT`, `num_of_clicks`, `num_of_impressions`.
* Когортные (по дате старта потока): `spend_USD_by_dt_potok`, `spend_KZT_by_dt_potok`, `num_of_clicks_by_dt_potok`, `num_of_impressions_by_dt_potok`.

**3. Воронка Лидогенерации (Regs, Apps, Checkins)**
* Регистрации: `num_of_regs` (все), `num_of_uniq_regs` (уникальные). Когортные: `num_of_regs_by_dt_potok`, `num_of_uniq_regs_by_dt_potok`.
* Заявки: `num_of_application`, `num_of_uniq_apps`. Когортные: `..._by_dt_potok`.
* Чекины (посещения вебинара): `num_of_checkins`, `num_of_uniq_checkins`. Когортные: `..._by_dt_potok`.

**4. Финансы и Сделки (Sales & Deals)**
Метрики продаж дублируются для 5 разных когорт (суффиксов). 

**Доступные суффиксы для сделок:**
* `_by_dt_of_payment` — атрибуция по дате фактической оплаты транша.
* `_by_dt_of_sale` — атрибуция по дате продажи (перехода сделки в успешный статус).
* `_by_dt_create` — атрибуция по дате создания лида (LTV-когорта).
* `_by_dt_close` — атрибуция по дате закрытия сделки.
* `_by_dt_potok` — атрибуция по дате старта потока.

**Список метрик внутри каждого суффикса:**
* `num_of_deals...` : Общее количество сделок.
* `num_of_prepayment...` : Количество внесенных предоплат.
* `num_of_succes_deals...` : Количество успешных сделок, (продаж).
* `num_of_clean_success_deals...` : Чистые успешные сделки, количество продаж, в которых не было возвратов.
* `sum_of_payment...` : Валовая сумма оплат (грязная выручка).
* `sum_of_refund...` : Общая сумма возвратов.
* `sum_of_clean_payment...` : Чистая выручка (оплаты минус возвраты).

**СЛОВАРЬ ТРИГГЕРОВ (Как выбирать суффикс по словам пользователя):**

1. **`_by_dt_of_payment`** (Атрибуция по дате фактической оплаты транша)

- **Запрос:** "Окупаемость по потокам"
  **Решение:** Используем исключительно метрики с суффиксом `_by_dt_potok`.
- **Запрос:** "Конверсия из заявки в продажу по когорте создания"
  **Решение:** Берем `num_of_application` и `num_of_succes_deals_by_dt_create`.

### 8. ПРАВИЛА СРАВНЕНИЯ ПЕРИОДОВ И СИНТАКСИС ДАТ
Если пользователь просит сравнить метрики за два разных периода (например, этот месяц с прошлым), КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО использовать `JOIN`. 
Используй условную агрегацию (Conditional Aggregation) внутри одного `SELECT`. 
Пример:
`SUM(CASE WHEN dt >= DATE_TRUNC(CURRENT_DATE(), MONTH) THEN sum_of_clean_payment_by_dt_of_payment ELSE 0 END) as current_month_revenue`

**КРИТИЧЕСКИЕ ПРАВИЛА ДАТ В BIGQUERY:**
1. Части дат (MONTH, DAY, YEAR) в функциях пишутся СТРОГО БЕЗ КАВЫЧЕК. 
   - Правильно: `DATE_TRUNC(dt, MONTH)`
   - Ошибка: `DATE_TRUNC(dt, 'MONTH')`
2. При вычитании или прибавлении дат ОБЯЗАТЕЛЬНО используй слово `INTERVAL`.
   - Правильно: `DATE_SUB(CURRENT_DATE(), INTERVAL 1 MONTH)`
   - Ошибка: `DATE_SUB(CURRENT_DATE(), 1 MONTH)`
